# 指令桥接层设计（据 615 所实习工作整理）

> 用途：把实习中的设计思路固化成可讲述、可复现的文档。
> 这不是单位代码，是**设计方案的还原**。代码归属单位，本文只描述方案与思路。

---

## 一、要解决的问题

航空建模软件的接口是给工程师用的：参数多、有前置条件、调用顺序有约束。

如果让大模型直接生成调用代码或自由文本参数，会崩在三个地方：

| 失败模式 | 后果 |
|---|---|
| 参数名写错 / 不存在 | 调用失败，或更糟——静默用了默认值 |
| 参数类型不对（字符串给了数字） | 接口报错，错误信息对用户无意义 |
| 指令顺序错（先倒角后建体） | 中间状态非法，软件崩溃或产生错误模型 |

**所以核心问题不是"怎么解析 JSON"，是"怎么让模型不可能生成非法指令"。**

---

## 二、三个设计决定

### 决定 1：把软件能力枚举成组件库

不把软件接口直接暴露给模型，而是先抽象成 **700+ 条指令**的集合：

```
组件库（Component Library）
├── 几何
│   ├── 创建体        create_body    {type, length, width, height}
│   ├── 倒角          fillet         {edge_ref, radius}
│   ├── 抽壳          shell          {face_ref, thickness}
│   └── ...
├── 约束
│   ├── 同心          concentric     {face_a, face_b}
│   └── ...
├── 材料
│   ├── 赋材料        assign_material{body_ref, material_id}
│   └── ...
└── ...
```

每条指令定死三件事：**名字、参数、参数类型**。模型只能从这份清单里选。

### 决定 2：受约束的生成

这是错误率近乎为零的根本原因。

| 做法 | 模型输出空间 | 结果 |
|---|---|---|
| 自由文本 | 无限 | 经常编出不存在的参数 |
| 只给提示词说"请用这些指令" | 仍然无限 | 大部分对，偶尔编 |
| **把组件库作为唯一可选集合** | **有限、且全部合法** | 几乎无格式错误 |

具体落地方式（三选一，按可约束强度递增）：

1. 提示词里给完整清单 + few-shot 示例
2. 工具调用 / function calling：把每条指令注册成一个工具
3. 受约束解码：解码时直接按 schema 屏蔽非法 token

**实习里用的是哪种，要能说清楚。** 如果记不清，就说"用组件库清单约束 + 输出后校验"这个组合。

### 决定 3：解析 + 校验层

模型即使被约束，也可能给出：必填项缺失、引用不存在的对象、数值越界。

所以中间必须有一层：

```
JSON 文本
   ↓ 解析（语法）
   ↓ 结构校验（是不是一条合法指令）
   ↓ 语义校验（参数类型 / 必填 / 取值范围 / 引用存在）
   ↓ 顺序校验（前置条件满足吗）
指令对象
   ↓ 调用
建模软件接口
```

**关键：每一层失败都要返回可读的错误，而不是抛异常或崩溃。**

## 三、指令 schema 长什么样

```json
{
  "op": "fillet",
  "id": "op_3",
  "args": {
    "edge_ref": "body_1.edge_12",
    "radius": 2.5
  }
}
```

对应的组件库条目：

```json
{
  "name": "fillet",
  "category": "geometry",
  "args": {
    "edge_ref": { "type": "ref",    "required": true,  "ref_kind": "edge" },
    "radius":   { "type": "number", "required": true,  "min": 0.01, "max": 1000 }
  },
  "preconditions": ["body_exists"]
}
```

**为什么带 `id`**：后面的指令要引用前面指令的产出（先建体，再对这个体倒角）。这是指令树能串起来的关键。

---

## 四、校验规则清单

按失败代价从高到低：

| 层 | 检查什么 | 失败返回 |
|---|---|---|
| 语法 | JSON 是否合法 | 行列号 + 上下文片段 |
| 结构 | 是否有 `op` / `args`，`op` 是否在组件库中 | `未知指令: xxx，可用指令见组件库` |
| 类型 | 参数类型是否匹配 | `参数 radius 期望 number，收到 string` |
| 必填 | 必填参数是否齐全 | `缺少必填参数: radius` |
| 范围 | 数值是否在 `[min, max]` | `radius=0 超出范围 [0.01, 1000]` |
| 引用 | `edge_ref` 指向的对象是否存在 | `引用的边 body_1.edge_12 不存在` |
| 顺序 | 前置条件是否满足 | `倒角需要先创建体，当前模型为空` |

## 五、因果链：为什么"几乎无错误"

这句话在面试里必须能拆成因果，不能只说结论。

```
组件库枚举了全部合法指令
   → 模型没有"编造参数"的空间
      → 语法层错误几乎不出现
         → 剩下的只有语义错误（引用、顺序、范围）
            → 校验层逐条拦下并给出可读错误
               → 到达软件接口的指令全部合法
                  → 实测几乎无错误
```

**注意**：这条链的前提是"模型真的只能在组件库里选"。如果你用的是提示词约束（不是受约束解码），那还有编造的可能，只是被校验层拦住了——说法要准确。

## 六、如果重做，我会改什么（面试加分项）

能批判自己的设计，比只讲成功更可信：

1. **组件库 700 条太扁平**：应该先分大类再做二级选择，模型一次只需在 20 条里选，准确率更高
2. **错误恢复只有报错**：可以把校验错误反馈给模型，让它自修正一轮，而不是直接失败
3. **缺少回放能力**：应该把每条执行过的指令存成可回放的脚本，便于复现问题和回归测试
4. **性能没测过**：700 条指令的查表如果是线性扫描，在长指令序列下会有明显开销

## 七、这套设计能回答的八个面试问题

| # | 问题 | 答案要点 |
|---|---|---|
| 1 | 为什么用 JSON 不用 protobuf？ | 大模型对 JSON 最熟，训练语料多；protobuf 需要 schema 文件，模型生成门槛高 |
| 2 | 700 条指令怎么组织？ | 按业务分类的树形结构，每条带参数 schema；查表 + 二级路由 |
| 3 | 怎么保证模型只输出合法指令？ | 组件库作为唯一可选集合；具体是提示词清单 / 工具调用 / 受约束解码中的哪一种 |
| 4 | 校验失败怎么办？ | 分七层拦截，返回可读错误；改进方向是反馈给模型自修正 |
| 5 | 参数类型怎么定？ | 组件库里每条参数声明 type / required / min / max / ref_kind |
| 6 | 指令有依赖怎么表达？ | 每条指令带 id，后续指令用 ref 引用前序产出；顺序校验检查前置条件 |
| 7 | 怎么调试一条错误指令？ | 错误信息带 JSON 路径 + 期望值 + 实际值 |
| 8 | 如果模型编了个不存在的组件？ | 结构校验直接拦下，返回"未知指令 + 可用清单" |

## 八、和 aegis-gateway 的关系

```
实习里：    LLM → JSON 指令 → 校验 → 建模软件
aegis-gateway：客户端 → JSON-RPC → 工具网关 → 下游工具（MCP server）
```

**同构的部分**：工具/指令注册、命名空间隔离、参数校验、错误映射、调用分发。

**不同的部分**：实习是单机调用本地软件，网关要走网络、有并发和超时。

所以 aegis-gateway 的定位写成「把实习方案一般化」是准确的，不是包装。
